## Pattern Overview

**Overall:** Content-driven CMS + Static Next.js Frontend with Server-Side Data Fetching

**Key Characteristics:**
- **Headless CMS approach:** Payload provides REST API + admin UI; Next.js consumes via `getPayload()`
- **Static generation with revalidation:** All pages pre-rendered via `generateStaticParams()`, updated on content changes with `revalidateTag()`
- **Locale-prefixed URLs:** All pages follow `/{locale}/{slug}` pattern; no locale prefix = redirect to default
- **Localized content:** Fields marked `localized: true` support per-language versions (en, mr)
- **Block-based page layouts:** Pages use composable blocks (array of polymorphic block types)
- **Server Components by default:** Data fetching happens in Server Components; minimal Client Components for interactivity

## Layers

**Backend (Payload CMS):**
- Purpose: Content management, user authentication, form submissions
- Location: `src/payload.config.ts`, `src/collections/`, `src/globals/`
- Contains: Payload configuration, collection schemas, global configs, hooks for revalidation
- Depends on: PostgreSQL, Cloudinary, Nodemailer
- Used by: Next.js API routes (`src/app/(payload)/api/[...slug]/route.ts`)

**API Layer (Next.js Routes):**
- Purpose: Expose Payload as RESTful/GraphQL API; handle custom endpoints
- Location: `src/app/(payload)/api/`, `src/app/(frontend)/next/`
- Contains: REST routes (auto-generated by Payload), GraphQL endpoint, preview routes, redirect resolution
- Depends on: Payload config, utilities
- Used by: Frontend pages and external clients

**Rendering Layer (Next.js App Router):**
- Purpose: Render frontend pages with data from Payload API
- Location: `src/app/(frontend)/`, `src/app/(payload)/admin/`
- Contains: Layout (with providers), page routes, static param generation, metadata generation
- Depends on: Payload API, utilities, components
- Used by: Browser requests

**Component Layer:**
- Purpose: Reusable UI units for rendering pages
- Location: `src/components/`, `src/blocks/`, `src/heros/`, `src/globals/`
- Contains: Page-level blocks (gallery, form, team, etc.), global components (header, footer), UI primitives
- Depends on: Tailwind CSS, Payload types, context providers
- Used by: Page components, other components

**Context/Provider Layer:**
- Purpose: Share state across component tree (locale, theme)
- Location: `src/providers/`
- Contains: Theme Provider (light/dark toggle), Locale Provider (current language)
- Depends on: React Context
- Used by: Root layout and child components

**Data Access Layer:**
- Purpose: Fetch data from Payload, apply caching and revalidation
- Location: `src/utilities/` (getGlobals, generatePageMeta, etc.)
- Contains: Helper functions to fetch collections/globals with `unstable_cache`, revalidation utilities
- Depends on: Payload API
- Used by: Page components, block components

**Internationalization:**
- Purpose: Multi-language support (English, Marathi)
- Location: `src/i18n/`
- Contains: Language configuration (single source of truth), default locale logic
- Depends on: Next.js headers for locale detection
- Used by: Layout, page components, Payload config

## Data Flow

### Primary Request Path (Page View)

1. **User requests** `/en/home` or `/mr/about` (`src/app/(frontend)/[locale]/[slug]/page.tsx`)
2. **Route matching** determines locale (`en` or `mr`) and slug (`home` or `about`)
3. **Server Component** calls `getPayload()` to instantiate Payload client
4. **Payload query** executed: `payload.find({ collection: 'pages', where: { slug: { equals: slug } }, locale, draft: false })`
5. **Data cached** via `unstable_cache()` with tag `global_pages` for ISR
6. **Render page layout:**
   - Fetch hero config from page data
   - Render `<RenderHero>` with hero variant (low/medium/high impact)
   - Render `<RenderBlocks>` with layout blocks array
7. **Block dispatch** in `RenderBlocks`: switch on `blockType` property to instantiate correct React component
8. **Component renders** with block data (richText, media, form fields, etc.)
9. **HTML sent** to browser; cached at CDN level via Next.js caching headers

**Key Files in Flow:**
- Entry: `src/app/(frontend)/[locale]/[slug]/page.tsx:36-47` (getPage function)
- Data cached: `src/utilities/getGlobals.ts:25-28` (unstable_cache with revalidation tags)
- Rendering: `src/components/RenderBlocks.tsx:32-47` (block dispatch)

### Static Generation Path

1. **Build time** (`next build`): `generateStaticParams()` called in `[locale]/[slug]/page.tsx`
2. **Query all pages:** `payload.find({ collection: 'pages', limit: 1000 })`
3. **Generate params:** Cross-product of languages × slugs = `[{ locale: 'en', slug: 'home' }, { locale: 'en', slug: 'about' }, { locale: 'mr', slug: 'home' }, ...]`
4. **Pre-render all** combinations at build time
5. **Revalidation triggers:** When content changes via CMS editor:
   - Payload hook fires (`src/collections/Pages/hooks/revalidatePage.ts`)
   - Calls `revalidateTag('global_pages')` to bust ISR cache
   - Next.js refreshes only affected page on next request

### Content Update Path

1. **Editor** saves page in Payload admin
2. **Payload afterChange hook** fires (`src/collections/Pages/hooks/revalidatePage.ts:revalidatePage`)
3. **Hook calls** `revalidateTag('global_<slug>')` and `revalidatePath('/(frontend)/<locale>/<slug>')` 
4. **Next.js cache busted** on next request to that route
5. **Page re-fetches** from Payload, renders fresh, served to next visitor
6. **Cloudinary images:** On Media upload, afterChange hook syncs to Cloudinary, stores `cloudinaryId`
7. **afterRead hook** overrides `url` property with Cloudinary delivery URL

### Static Page Generation Path (Locale Redirect)

1. **User requests** `/` (no locale)
2. **Root page component** (`src/app/(frontend)/page.tsx`) calls `getDefaultLocale()`
3. **Redirect** to `/${defaultLocale}` (e.g., `/en`)
4. **No render needed** — just redirect response

**State Management:**
- **No global mutable state** — fully deterministic, hydration-safe
- **URL state:** Locale via `[locale]` segment; slug via `[slug]` segment
- **Context state:** Theme (light/dark, stored in localStorage + document.documentElement.data-theme), Locale (read from headers)
- **Cache state:** Payload responses cached with revalidation tags

## Key Abstractions

**Block Pattern:**
- Purpose: Make pages composable from a set of predefined, reusable content blocks
- Examples: `src/blocks/Content/`, `src/blocks/Gallery/`, `src/blocks/Form/`
- Pattern: Each block has `config.ts` (Payload schema, defines fields) and `Component.tsx` (React component to render). Pages store array of blocks; `RenderBlocks` dispatches to correct component based on `blockType`.

**Hero Pattern:**
- Purpose: Allow pages to have optional hero section with variants (none/low/medium/high impact)
- Examples: `src/heros/LowImpact.tsx`, `src/heros/HighImpact.tsx`
- Pattern: Defined in Payload as a group field (`src/heros/config.ts`). Hero type selects which React component renders. `RenderHero` dispatches.

**Access Control Pattern:**
- Purpose: Role-based permissions for CMS actions (create, read, update, delete)
- Examples: `src/access/isAdminOrHigher.ts`, `src/access/isEditorOrHigher.ts`
- Pattern: Each Payload collection has `access` property with functions like `create: isEditorOrHigher`. Functions receive user object, return boolean.

**Localization Pattern:**
- Purpose: Support multiple languages without duplicating schemas
- Examples: `title: { type: 'text', localized: true }`
- Pattern: Payload handles multi-locale data storage automatically. Fields marked `localized: true` are stored per-locale. Queries specify `locale` parameter. Frontend reads from URL segment.

## Entry Points

**Frontend Entry:**
- Location: `src/app/(frontend)/layout.tsx`
- Triggers: Browser request to any `/[locale]/...` path
- Responsibilities: Establish root HTML, load providers (Theme, Locale), fetch globals (Header, Footer), set up fonts, GA tracking

**API Entry:**
- Location: `src/app/(payload)/api/[...slug]/route.ts`
- Triggers: REST requests to `/api/...` paths
- Responsibilities: Proxy all requests to Payload, handle authentication, return JSON

**Admin Entry:**
- Location: `src/app/(payload)/admin/[[...segments]]/page.tsx`
- Triggers: Requests to `/admin`
- Responsibilities: Serve Payload admin UI (auto-generated)

**Form Submission Entry:**
- Location: Form blocks submit to Payload Form Builder API
- Triggers: User submits form via block
- Responsibilities: Validate, store in Payload, send email (if configured via nodemailer)

**Image Processing Entry:**
- Location: Cloudinary hooks in `src/collections/Media.ts`
- Triggers: Media file uploaded/updated
- Responsibilities: Upload to Cloudinary, generate variants, override URL

## Architectural Constraints

- **Threading:** Node.js single-threaded event loop. Async/await for all I/O. Sharp image processing uses worker threads internally.
- **Global state:** Payload config is a module-level singleton. Theme state stored in localStorage and DOM attribute. Locale state in URL + request header. **No global mutable variables in components.**
- **Circular imports:** None detected. Layer boundaries are strict: Components import utilities, not vice versa. Payload config imports collections, not vice versa.
- **Database transactions:** Payload handles at its level; code doesn't manage transactions explicitly.
- **Cache invalidation:** Relies on `revalidateTag()` and `revalidatePath()` — manual, not automatic. Must add hooks to each collection/global that affects frontend.
- **Type safety:** Full TypeScript. Payload auto-generates `src/payload-types.ts` (run `pnpm generate:types` after schema changes).
- **Rendering mode:** Server Components by default. Client Components (`'use client'`) only for interactivity (Theme toggle, Locale toggle, Form inputs).

## Anti-Patterns

### Fetching in Root Layout Lazily

**What happens:** If a utility function like `getCachedGlobal('header')` is called without proper cache setup, every page request re-fetches from the database.

**Why it's wrong:** This defeats the purpose of ISR. The header should be cached and only invalidated when Header global changes.

**Do this instead:** Always use `unstable_cache()` with revalidation tags in utility functions (`src/utilities/getGlobals.ts`). Pair with `revalidateTag('global_<slug>')` in Payload hooks.

### Putting Payload Admin Inside Next.js Page Routes

**What happens:** If someone tries to manage Payload routes in `src/app/admin/page.tsx` manually instead of using Payload's built-in admin route.

**Why it's wrong:** Payload admin needs its own layout, permissions, and assets. Payload already serves this at `src/app/(payload)/admin/[[...segments]]/page.tsx`.

**Do this instead:** Leave Payload admin routing to Payload. Use the `src/app/(payload)/admin/[[...segments]]/page.tsx` route group.

### Hardcoding Locales in Components

**What happens:** If a component uses `locale: 'en'` as a hardcoded string instead of reading from context or props.

**Why it's wrong:** When a page is rendered in a different locale, hardcoded strings break. Multi-language support becomes fragile.

**Do this instead:** Use `getLocale()` in Server Components or `useLocale()` in Client Components. Pass locale via props if needed.

### Skipping Migrations After Schema Changes

**What happens:** If a field is added to a Payload collection but `pnpm payload migrate` is skipped, the database schema doesn't match the code schema.

**Why it's wrong:** Payload `push: false` is set in config. Automatic schema sync is disabled. Code will expect a field that doesn't exist in the database.

**Do this instead:** After any schema change, run `pnpm payload migrate:create`, review the migration, then `pnpm payload migrate`. Then `pnpm generate:types`.

## Error Handling

**Strategy:** Try-catch at API boundaries; return safe defaults in components; log errors server-side.

**Patterns:**

1. **Payload queries:** Wrap in try-catch. If page not found, call `notFound()` to show 404.
   ```typescript
   const result = await payload.find({ collection: 'pages', where: { slug: { equals: slug } } })
   if (!result.docs.length) notFound()
   ```

2. **Cloudinary uploads:** Catch in afterChange hook, log error, return doc unchanged. Image delivery falls back to local if cloudinaryId missing.

3. **Form submissions:** Payload Form Builder handles validation. If submission fails, error returned to browser, displayed in form.

4. **Missing i18n:** If locale not in LANGUAGES array, call `notFound()` (see `[locale]/page.tsx` line 46).

5. **Missing components:** In RenderBlocks, if blockType doesn't match any known block, return null (don't crash).

## Cross-Cutting Concerns

**Logging:** 
- Payload admin UI logs to browser console
- Server errors logged to Node.js stderr (visible in `pnpm dev` or deployment logs)
- Errors in Cloudinary sync logged in afterChange hook
- No persistent log storage configured

**Validation:**
- **CMS level:** Payload field-level validation (required, minLength, pattern, etc.)
- **API level:** Payload REST API validates against schema
- **Frontend level:** React Hook Form in form blocks; HTML5 input validation
- **Custom:** Form blocks use field-specific components (Country, State, Email) with options validation

**Authentication:**
- **Admin access:** Payload built-in user/password auth
- **Public access:** Pages readable without auth (via `access: { read: authenticatedOrPublished }`)
- **Form submissions:** Public (no auth required to submit)
- **Media:** `access: { read: anyone }` — all images public
